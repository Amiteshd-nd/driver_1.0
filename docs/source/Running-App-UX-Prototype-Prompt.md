# Running App — UX Prototype Workbench Prompt

Paste this into Claude Code in the same project where Phase 1 lives. Attach **Running-App-UX-Prototype-PRD.md** and **Running-App-PRD.md**.

---

> Phase 1 is done. We're now designing the full user interface and user experience as a web prototype. Read **Running-App-UX-Prototype-PRD.md** fully first; it is the spec for this work. Use **Running-App-PRD.md** for product context. I am a designer, not a developer, so make the technical decisions and explain things simply.
>
> **Step 1 — Design phase, before any screens.** Spin up specialised sub-agents acting as a product designer, a UX designer and a UI designer, each applying the real best practices of that role. Have them produce, as markdown files in `/docs`: user personas (based on the six dummy users in the product PRD), end-to-end user journeys for the whole app, a complete screen inventory with each screen's purpose, entry/exit points and states, and an interaction spec listing every animation, toast and notification per screen with the use case that triggers it. Show me the screen inventory and journeys and wait for my okay before building.
>
> **Step 2 — The workbench.** Build a Flutter web prototype with three columns. Left panel: a list of every page from the inventory, grouped by journey; clicking one loads it. Centre: a realistic phone frame running the live, fully clickable app screens, with a reset button and a "simulate run" control (pace, distance, time of day, location) so I can trigger card reveals on the web. Right panel: the selected page's properties, which change depending on the page selected — animation durations, delays and easing; toast and notification durations and text; and the trigger (use case) that fires each action, chosen from a dropdown, with a "fire this trigger" button to preview it. Changes must update the phone frame instantly and persist to a single `interaction-config.json`. The left and right panels sit outside the phone frame.
>
> **Step 3 — Design system package.** Create a separate, importable package (`/design_system`) that the production app will reuse: colour, typography, spacing, radius, elevation and motion tokens in light and dark; rarity and tier tokens (common/rare/epic/legendary, foil and shimmer, baby-to-adult sizing); all components (including the animal card with slots for art, serial number, run stats, flavour line and set name; toasts; bottom sheets; search field; stat tiles; progress rings; celebration overlay); and reusable patterns (card reveal, growth celebration, permission flow, share poster with no map). Components must read only from tokens, so a new rarity or tier means new tokens, not new components. Add a living catalogue page in the workbench that shows every token and component with all variants and states.
>
> **Constraints.** Prototype only: mock data that mirrors the Phase 1 data shapes, including the six dummy users; no real GPS, health or Supabase calls. Use clear placeholder animal art at correct sizes. Keep the repo structured as `/app`, `/design_system`, `/workbench`, `/docs`. Finish with a README on how to run it and how to add a page or a component. When done, tell me exactly how to open it and what I should see.
